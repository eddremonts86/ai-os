# Repobeats – self-hostable GitHub activity cards in Rust

> Auto-generated product brief. Review and refine before MVP scoping.

## Value Proposition

An embeddable SVG card showing a repository's commits, issues and pull requests, generated by a service the operator runs and can inspect end to end. The author built it after cards he relied on from the hosted original stopped updating consistently, so the design goal is control over collection, storage, caching and rendering rather than a new visual style.

Connecting a repository is an explicit read-only GitHub App install. Installation tokens are short-lived and never stored. A small deployment runs on SQLite with an in-process cache; a multi-instance deployment runs on PostgreSQL with optional Redis. Cards come in several themes, sizes and time ranges and ship with ETags so a README embed revalidates instead of re-rendering.

**One-liner:** Repobeats renders your repository's activity as an embeddable SVG from a pipeline you host and can inspect, so a card that stops updating is a bug you can find.

## Jobs To Be Done

1. **Functional job** — Show a repository's recent activity in its README without depending on a third-party service staying healthy.
2. **Functional job** — Notice, and then diagnose, a card that has stopped updating.
3. **Functional job** — Run the whole thing on one small machine, and later on several, without changing tools.
4. **Emotional job** — Stop wondering whether the numbers on the README are current.
5. **Social job** — Signal an active project to visitors with a graphic that is demonstrably self-hosted and open source.

## Success Metrics

- **Refresh freshness** — share of connected repositories whose last successful refresh is inside the configured interval. This is the metric the project exists for; the hosted original failed exactly here.
- **Duplicate collection rate** — GitHub API calls per repository per interval divided by replica count. Anything above one means the scheduler is not coordinating.
- **Conditional-request hit rate** — proportion of collection calls answered by GitHub as unchanged, which is what keeps the installation inside its rate limit.
- **Card revalidation rate** — share of card requests answered with a 304 rather than a re-render, since README embeds are fetched by image proxies at high volume.
- **Install completion** — installs started versus finished, given the author names the opt-in flow as the part he most wants feedback on.
- **Self-host success** — reported deployments that reached a rendering card without the operator filing an issue about setup.

## Pricing & Monetization

The post names no price, no tier and no hosted plan; it is an open-source, self-hostable project shared for feedback. What the architecture does fix is the cost shape: collection volume scales with connected repositories rather than with viewers, because card serving is cached and revalidated, while GitHub API budget is consumed per installation. Any future hosted offering would therefore have to be bounded per connected repository, not per seat.

## Competitive Landscape

- **The hosted original the author was using** — still online by his own account, and the reason for this project is not that it is bad but that some cards he relied on were no longer updating consistently and he could not inspect why.
- **GitHub's own repository insights** — richer analysis, but not embeddable, so it does not solve the README problem.
- **Generic README badge and shield services** — embeddable and widely used, but they render a single value rather than an activity series, and they are hosted services with the same inspectability gap.

The post names no competitor beyond the original, so no further comparison is claimed here.

## Risks & Open Questions

- [ ] Decide how refresh work is assigned across replicas — leased rows, a distributed lock, or consistent hashing — since the author names this as his open problem.
- [ ] Confirm the install screen states the public-card consequence clearly enough for private-repository owners before they consent.
- [ ] Establish what happens to a card when collection has been failing for several intervals: stale render, explicit staleness marker, or error card.
- [ ] Verify the SVG renders identically through GitHub's image proxy, which strips and re-serves content, on every supported theme.
- [ ] Measure whether the SQLite path really holds at the top of its intended range, and document the point where PostgreSQL becomes necessary.
- [ ] Decide whether disconnecting the GitHub App deletes collected history or retains it, which is a data-retention promise the install flow has to make.
