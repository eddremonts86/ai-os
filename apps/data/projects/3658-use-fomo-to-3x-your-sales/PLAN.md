# Use FOMO to 3x your sales

## Tech Stack

- **Next.js with TypeScript** for the merchant dashboard and the widget host, because the project is a web microsaas and Next.js covers both the merchant UI and the widget delivery path.
- **PostgreSQL with Prisma** for merchant data, integration connections and the event log, because relational integrity matters for an event-log product and Prisma gives a typed data layer.
- **Stripe Connect webhooks** for the Stripe integration, with signature verification, idempotent event processing, and a retry path for missed deliveries.
- **WooCommerce REST API** for the WooCommerce integration, authenticated per-merchant and polled or webhook-driven depending on what the connected store supports.
- **Edge runtime webhooks** for the ingestion endpoint, so the per-event latency stays low and the merchant sees notifications quickly after the real event.
- **A lightweight widget script** delivered as a small JS bundle that the merchant drops onto their storefront, with a documented CSP-friendly version and a fallback for stores that cannot run third-party scripts.
- **An event-sourced notification log** as the audit trail that backs the "fake events are impossible by construction" claim: every rendered notification is traceable to a real upstream event with an immutable record.

## Architecture

The capture path is the heart of the product: real events flow from the merchant's connected integrations into FomoToast, and the widget renders them as notifications on the storefront. Each integration has its own ingestion path because the source shapes are different. Stripe delivers signed webhooks that are verified on receipt, deduplicated against the event log, and stored with their full payload so the audit trail is complete. WooCommerce delivers events either through its own webhook support (preferred) or through a polling fallback for stores where webhooks are not configured; either way, the events are stored with the same schema as Stripe events so the rest of the pipeline is integration-agnostic.

A rendered notification is generated by selecting a recent event from the event log, applying the merchant's rules (which event types show, how recent, what PII to redact), and emitting a small payload to the widget. The widget polls or subscribes for new notifications over a low-latency channel and renders them with the merchant's chosen design. Every rendered notification has a trace back to the upstream event in the event log; the system makes fake events impossible by construction because the notification payload is generated server-side from the event log, not from anything the merchant can write directly.

The merchant dashboard surfaces three things. First, the connected integrations and their health (last event received, last webhook delivered, last error). Second, the recent notifications rendered, with the underlying event each one traces to, so the merchant can see the system is working and can audit any specific notification. Third, an A/B or before/after uplift measurement that uses the merchant's own traffic — this is where the product's credibility lives, because it is the merchant's measurement, not vendor copy.

Privacy is a first-class surface. Notifications can include customer names or locations by default, and that has to be a merchant choice, not a default. The system supports placeholders ("Someone in {region} just purchased") and full redaction, and the merchant's choice is enforced server-side so a tampered widget cannot reveal what the merchant has chosen to hide. Frequency caps and quiet hours are merchant-configurable so a noisy storefront is not the default.

## Milestones

1. **M1 — Stripe ingestion** — Stripe Connect webhook intake with signature verification, idempotent event processing, and the event log schema.
2. **M2 — WooCommerce ingestion** — WooCommerce REST API integration with webhook support where available and a polling fallback.
3. **M3 — Notification engine** — server-side selection, rules, PII redaction, and the traceable-from-event-log property.
4. **M4 — Widget** — a small JS bundle with a CSP-friendly variant and a fallback for stores that cannot run third-party scripts.
5. **M5 — Merchant dashboard** — integrations health, recent notifications with their upstream events, and the in-dashboard uplift measurement.
6. **M6 — Privacy controls** — placeholder/redaction options, frequency caps, quiet hours, all enforced server-side.
7. **M7 — Roadmap page** — a public status page for upcoming integrations (shipped / in progress / planned) so the post's "more integrations coming soon" is honest.

## Risks

- **Fake-event injection** — the headline trust failure of the category; the architecture has to make it impossible by construction, not by policy.
- **Webhook delivery gaps** — missed webhooks mean missed notifications; the system needs a polling fallback for WooCommerce and a reconciliation pass for Stripe.
- **PII leakage** — showing a real customer's name or address in a notification is a privacy incident; redaction has to be server-enforced.
- **"3x" credibility** — restating the title's claim as a product metric would invite scrutiny the project cannot meet; the uplift surface has to be the merchant's own measurement.
- **Widget compatibility** — the storefront that breaks the widget loses the merchant; CSP, third-party-script blockers, and platform-specific quirks are real failure modes.
- **Scope creep on integrations** — promising every integration the merchant asks for would dilute the launch; the roadmap has to be public and limited.
- **Microsaas operational load** — a small team has to keep the integrations healthy without on-call rotations; the event log and dashboards have to make failures visible without paging anyone.
