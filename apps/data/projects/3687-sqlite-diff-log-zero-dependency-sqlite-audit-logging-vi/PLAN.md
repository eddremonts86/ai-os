# SQLite-diff-log – zero-dependency SQLite audit logging via triggers

## Tech Stack

- **Language:** Python 3.8+ (stdlib only at runtime: `sqlite3`, `json`).
- **Audit mechanism:** SQLite native `AFTER INSERT / UPDATE / DELETE` triggers, generated by Python and installed with `CREATE TRIGGER IF NOT EXISTS`.
- **Packaging:** `pyproject.toml` + setuptools, published to PyPI as `sqlite-diff-log`. No compiled extensions.
- **Testing:** `unittest` (stdlib), executed via `python -m unittest test_sqlite_diff_log.py`. CI on GitHub Actions across the Python version matrix.
- **Documentation:** README.md on the repository (mirrored to PyPI long description), LICENSE (MIT).

## Architecture

The package is a thin Python wrapper that emits SQL. On `attach_to_table(table, pk_col)`, it reads the column list from `PRAGMA table_info(table)` (validated against `sqlite_master`), quotes identifiers, and runs three `CREATE TRIGGER IF NOT EXISTS` statements that fire `AFTER INSERT / UPDATE / DELETE` on `table`. Each trigger builds a `json_object(...)` snapshot of `OLD.*` / `NEW.*` and inserts a row into `_audit_log` (auto-created on `SQLiteDiffLog(conn)` instantiation). Because the trigger lives inside the database, every writer — Python, Node, Go, the `sqlite3` CLI — is covered without further cooperation.

```
+---------------------+      SQL write        +-----------------------+
|  Any writer         | --------------------> |  Target table         |
|  (Python, Node,     |   INSERT/UPDATE/      |  (e.g. users)         |
|   Go, sqlite3 CLI)  |    DELETE             +-----------------------+
+---------------------+                                  |
                                                          | AFTER triggers (installed once)
                                                          v
                                          +------------------------------+
                                          | _audit_log (same .db file)   |
                                          |  id, table_name, action,     |
                                          |  row_id, old_data, new_data, |
                                          |  created_at                  |
                                          +------------------------------+
                                                          ^
                                                          |  json_object(OLD.* / NEW.*)
                                          +------------------------------+
                                          |  attach_to_table()           |
                                          |  SQLiteDiffLog(conn).        |
                                          |  get_logs(table)             |
                                          +------------------------------+
```

## Milestones

2. **M1 — Trigger installation + idempotency.** `attach_to_table` working with quoted identifiers, `PRAGMA table_info` validation, `IF NOT EXISTS` so re-runs are safe. End of week 2.
3. **M2 — Audit row emission + JSON snapshots.** `INSERT/UPDATE/DELETE` produce `_audit_log` rows in the same transaction; `old_data`/`new_data` round-trip through `json`. End of week 3.
4. **M3 — get_logs() reader + filtering.** Parsed dicts, optional table filter, ordering by `created_at`. End of week 4.
5. **M4 — Cross-process test.** Test that a Node subprocess or a second `sqlite3` connection produces audit rows without going through Python. End of week 5.
6. **M5 — PyPI publish + Show HN launch.** Tag `v0.1.0`, push to PyPI, post Show HN (already happened 2026-08-28). End of week 6.

## Risks

- **Identifier injection.** A naive string-template of column names into `json_object(...)` would let a maliciously-named column break the trigger. Mitigation: quote identifiers with `"` and validate they exist in `sqlite_master` before issuing the trigger; literals are escaped via SQLite parameter binding.
- **Schema drift.** Adding a column to an attached table does not retroactively update the trigger's `json_object(OLD.*)` call. Mitigation: documented procedure to call `attach_to_table` again after a schema change; v0.2 candidate feature is a `rebuild_triggers(table)` helper.
- **Composite primary keys.** Current implementation assumes a single PK column. A table with `PRIMARY KEY (a, b)` will fail validation today. Mitigation: explicit `ValueError` with a "not yet supported" message; tracked as v0.2 scope, not silently broken.
- **Audit-log bloat.** `_audit_log` has no retention policy. A long-lived embedded deployment can run the file past its backup budget. Mitigation: document the growth rate (one row per write, ~one JSON snapshot) and leave pruning to the application; a v0.2 helper may add TTL-based archival.
- **"Who changed this" cannot be answered by the trigger alone.** SQLite triggers have no session context. Mitigation: documented expectation that the application carries an `updated_by` column; the package does not paper over it.
- **Replication lag is not the package's responsibility.** Litestream / Turso replication is independent. Mitigation: keep audit rows in the same file (already true) so replication carries them as part of the WAL.
