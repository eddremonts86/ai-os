# A freelancer often loses in proposal competitions due to the inability to quickly create personalized and visual website concepts for each job order.

## Tech Stack

- **Next.js (App Router)** for the web app, chosen because the preview surface and the per-brief folder are both server-rendered paths that benefit from the App Router's data co-location.
- **TypeScript** end-to-end, because the concept template engine and the brief-parse step have enough branching that untyped code is the wrong shape.
- **Tailwind CSS** for the generated concepts, because a styled-rather-than-painted concept is the cheapest way to keep the freelancer's house-style presets consistent across concepts.
- **Playwright (headless screenshots)** for the static-screenshot export, because a screenshot is a single-pass render of the live concept and headless Chromium produces a result that matches the hosted preview.
- **Stripe** for the subscription and credit billing, because the source names no billing preference and Stripe is the cheapest pragmatic choice for a B2C subscription plus consumption model.
- **S3** for the per-pitch storage of briefs, generated concepts, and screenshot artefacts, because the freelancer's library grows over months and a flat object store is the cheapest shape.
- **OpenAI GPT-4o-mini** for the brief-parse and concept-generate pipeline, because a small instruction-tuned model handles brief-to-structure transformation and the freelancer's iteration loop needs latency on the order of seconds.

## Architecture

The freelancer pastes a job-order brief into the ingest surface. The brief is parsed into a structure (deliverable type, audience, tone, the lines that are likely to be quoted back) and the parsed structure is sent to a generator that produces a single-page HTML/CSS concept. The persona-detection step classifies the deliverable (landing page, multi-page site, app screen, brand mark) and routes the generator to the right template set, so the freelancer does not pick one per pitch.

The preview surface shows the live concept on the right and the brief on the left, with the freelancer's edits applied on top. Each edit is a small patch — change a headline, swap a colour, reorder a section, swap a typeface — and the underlying HTML/CSS is the single source of truth so the screenshot export and the hosted preview URL render the same artefact. The edit surface is keyboard-first; the freelancer's deadline rhythm is second-by-second and a modal-based editor breaks that.

A hosted preview URL is short-lived by design (a configurable number of days, defaulting to fourteen) and uses an unguessable slug the freelancer can paste into a proposal. After expiry, the URL resolves to a 'this pitch is older' surface rather than a dead link, because a freelancer whose link arrives late is the failure mode a hard expiry creates. A static screenshot is generated by Playwright rendering the same HTML/CSS at a chosen viewport, so the screenshot matches what the hosted preview shows.

The freelancer's library of saved style presets is what makes the tool distinct from a template generator. Each preset is a small bundle of typography, colour, and section-order defaults, and the freelancer can save their own from any concept they are happy with. The preset is applied at concept generation time, so subsequent pitches take the freelancer's house style for granted rather than requiring per-pitch choices.

Asset licensing is enforced at generation time. The font choice, the imagery source, and the code patterns shipped in the concept are constrained to assets the freelancer can use commercially without a separate agreement, and the constraint is visible in the editor so the freelancer can see what they have.

## Milestones

1. **M1 — Brief ingest and parse** — Paste, URL, or free-text brief; structured output with deliverable type, audience, and tone.
2. **M2 — Persona and template routing** — Persona-detection step that routes the parsed structure to the right template set.
3. **M3 — Generator** — Single-page HTML/CSS concept generation with applied style preset and populated brief content.
4. **M4 — Live preview and edit surface** — Side-by-side brief and live concept; keyboard-first edit surface; preset save.
5. **M5 — Hosted preview and screenshot** — Short-lived hosted URL with unguessable slug; Playwright-rendered screenshot at chosen viewport.
6. **M6 — Per-pitch library** — Per-brief folder with brief, concept, screenshot, and exports; revisit previous pitches.
7. **M7 — Asset license enforcement** — Restricted fonts, imagery, and code patterns enforced at generation time with a visible constraint surface.

## Risks

- **Asset license drift** — a generated concept that uses a font or stock image the freelancer cannot pitch is unfit; the constraint has to be enforced at generation, not flagged after.
- **Brief-parse accuracy** — a brief that is misread into the wrong deliverable type produces the wrong concept; persona-detection has to be auditable per brief.
- **Hosted URL lifetime** — a pitch arriving six months later must resolve to something; the after-expiry surface cannot be a dead link.
- **Review gate** — a tool that exports without review can be used to send pitches the freelancer has not actually read; the export step has to require at least one save.
- **Brief content sensitivity** — brief text sometimes contains client-confidential information; per-brief storage has to be controllable by the freelancer.
- **Iteration latency** — each edit must render the live concept in seconds; latency above a few seconds breaks the freelancer's deadline rhythm.
- **Concept uniqueness** — a template generator that produces identical concepts for similar briefs becomes obvious across pitches; per-brief variation has to be content-driven, not just preset-driven.
- **Screenshot fidelity** — a screenshot that does not match what the hosted preview shows is a usability failure; both paths must render the same artefact.
