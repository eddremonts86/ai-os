# AI-OS

The local AI Operating System that turns a Mac into a multi-agent
research/workstation. Built on the **Spec → Verifier → Environment**
method. This is a detailed technical reference. `CLAUDE.md` is the master
operating instruction, and the repository root should be referenced as
`$AI_OS_ROOT` (typically `$HOME/Projects/ai-os`).

---

## 1. What AI-OS is

AI-OS is **not** an agent. It is the **operating substrate** an agent
runs on:

- A folder structure (`CLAUDE.md`, `AGENTS.md`, `context/`, `specs/`,
  `verifiers/`, `rules/`, `skills/`, `workflows/`, `outputs/`, `archive/`)
- A persistent-memory stack (FalkorDB graph DB + Ollama embeddings +
  codebase-memory-mcp + grepai)
- A loop orchestration CLI (`ai-os loop`)
- A memory sub-system CLI (`ai-os memory`)
- A set of vendored skills + MCPs that any agent can load

The agents (Claude Code, Hermes, Codex, Gemini, Antigravity, OpenCode,
Aider, Cursor, Zed) all read `AGENTS.md` / `CLAUDE.md` and follow the
same Spec→Verifier→Environment loop. This means **a Spec written for
Hermes is reusable in Claude Code** without translation.

## 2. Top-level architecture

```
$AI_OS_ROOT/
├── AGENTS.md                       # instructions for AI agents (read first)
├── CLAUDE.md                       # alias of AGENTS.md (Claude Code convention)
├── context/                        # durable per-user context (profile, prefs,projects,tools)
├── rules/                          # hard rules: always_do / ask / never_do / loop_safety
├── specs/                          # one active Spec + current_spec.md
├── verifiers/                      # quality gates (post-task)
├── skills/                         # local skills (workspace-specific)
├── workflows/                      # recurring processes (project_start, daily_start, etc)
├── archive/                        # completed Specs
├── outputs/                        # generated artifacts (research reports, loop outputs)
├── prompts/                        # original Karpathy prompts (English reference)
├── ai-config/                      # AI config: skills/ (distributable), MCPs,commands
│   ├── clis/                       # per-CLI overlays (minimax-overlay.md)
│   ├── templates/                  # bridge/SOUL templates rendered per machine
│   ├── commands/                   # slash-command definitions
│   ├── mcp/                        # MCP server YAML configs (10 servers)
│   └── skills/                     # skill bundles (compatible with all agents)
├── dev-env/                        # dev env: dotfiles, Brewfile, packages, .env.example
├── setup/                          # install scripts (install-mac.sh, verify.sh, etc)
├── vendor/                         # third-party vendored skills (gstack, ecc, codex-plugin-cc)
├── .github/                        # CI workflows (test-mac/linux/windows)
└── docs/                           # documentation (this file lives here)
```

The `~/.hermes/`, `~/.local/bin/`, and `~/.zshrc` are the runtime
surface — they are **not** in the AI-OS repo on purpose. The repo
contains the source-of-truth; the home directory contains the
deployed artifacts.

## 3. The persistent-memory stack (phase 1)

The memory stack is the most concrete deliverable in AI-OS. Four
services, four ports, one CLI to manage them.

### 3.1 What runs

| Service | Port | Process | Purpose |
|---|---|---|---|
| **FalkorDB** (graph DB) | `3300` (Web UI), `6390` (Redis protocol) | `docker compose` | Stores entities + relationships (decisions, projects, components) |
| **Ollama** (embeddings) | `11500` | `ollama serve` | Generates 768-dim vectors with `nomic-embed-text` |
| **codebase-memory-mcp** | `9749` (UI), `9749` (REST API) | `~/.local/bin/codebase-memory-mcp` | Builds a knowledge graph of code (functions, calls, imports) via tree-sitter + Hybrid LSP |
| **grepai** | n/a (CLI binary) | `~/.local/bin/grepai` | Privacy-first semantic code search (Nomic `nomic-embed-code` baked in) |

**Port assignments are deliberate**: AI-OS reserves `3000-3050` for
web apps. Memory services live in `3000-3999` (web), `6300-6900` (db),
`11000-11999` (AI). `6390` (FalkorDB Redis) and `3300` (FalkorDB Web)
and `11500` (Ollama) and `9749` (cbm UI) and `3990` (codebase-mcp TCP)
are all in their reserved ranges.

### 3.2 Installing the memory stack

The `setup/install-mac.sh` script is idempotent. Re-run it any time.

```bash
# From a fresh Mac (or fresh shell):
cd /Users/edd/Projects/ai-os
bash setup/install-mac.sh

# Verify:
bash setup/verify.sh
# Expected: 38 passed, 0 failed.
# Banner: "AI-OS is correctly installed. 🎉"
```

The script:

1. Installs Homebrew packages from `dev-env/packages/Brewfile` (docker, ollama, uv, etc.)
2. Creates symlinks in `~/.local/bin/` for `codebase-memory-mcp`, `grepai`, `ai-os`, `ai-os-loop`
3. Starts the FalkorDB container via `docker compose -f memory/falkordb/docker-compose.yml up -d`
4. Starts `ollama serve` on `127.0.0.1:11500` (background, logs to `/tmp/ollama-server.log`)
5. Pulls `nomic-embed-text` model (274 MB) into Ollama
6. Downloads `codebase-memory-mcp` v0.8.1 (darwin-arm64) and `grepai` v0.35.0 to `~/.local/bin/`
7. Generates `~/.hermes/config.yaml` from `ai-config/mcp/*.yaml` (10 MCPs total: 7 existing + 3 memory-related)
8. Adds an `ai-os` alias to `~/.zshrc` so the CLI is on PATH
9. Adds a self-healing PATH block to `~/.zshrc` so `codebase-memory-mcp` and `grepai` resolve even when `~/.local/bin` is missing from PATH (e.g. under `env -i` from MCP loaders)
10. Registers a `cron-reindex.sh` (currently manual, cron creation is up to the user)

### 3.4 The `ai-os memory` CLI

```
ai-os memory <subcommand> [args]
```

| Subcommand | Purpose |
|---|---|
| `status` | Service health + node counts + MCP registration status |
| `browse` | Open FalkorDB Web UI in default browser |
| `visualize` | Open FalkorDB UI + cbm UI (if daemon running) + grepai status |
| `start` / `stop` | FalkorDB container lifecycle |
| `logs` | Tail FalkorDB logs |
| `query "<q>" [path]` | Semantic search via grepai (requires `grepai watch` running) |
| `search "<q>" [path]` | Same as `query`, but falls back to codebase-memory-mcp if grepai isn't running |
| `reindex [path]` | Index a repo into codebase-memory-mcp (calls `index_repository` tool) |
| `sync-sessions [N]` | Ingest last N days of Hermes session DBs into the graph |

#### Subcommand behavior detail

**`reindex`**: reindexes the AST of a directory. Example:

```bash
ai-os memory reindex /Users/edd/Projects
# Output:
#   index_status: nodes=568452 edges=2053993 size_bytes=1452998656
# This is a 1.45 GB graph covering 4 top-level projects.
```

**`search`**: tier 1 (grepai live daemon) → tier 2 (codebase-memory-mcp).
The CLI auto-detects which is available. Tier 2 returns structured
JSON with qualified names, in_degree / out_degree, and full file
paths. Deduplication ratio is typically ~10x (500 raw matches →
50 functions).

**`visualize`**: opens three things in your browser:
1. FalkorDB UI (`http://localhost:3300`)
2. codebase-memory-mcp UI (`http://localhost:9749`) — only if a daemon
   with `--ui=true` is alive (usually only when Hermes chat is open)
3. Reports `grepai` daemon status (not browser-accessible)

**Note on the cbm UI**: this UI is **not** a static graph viewer. It's
a single-page React app that fetches `/api/*` REST endpoints and
renders a 3D graph. Requires the daemon to be running with
`--ui=true`. Normally only when `hermes chat` is open.

### 3.5 Working around the cbm "project not found" bug

`codebase-memory-mcp` v0.8.1 has a known bug: tools like `search_code`
and `search_graph` fail with `"project not found or not indexed"`
even when `list_projects` shows the project. Workarounds:

1. Use the daemon mode (start Hermes chat → cbm stays alive with
   consistent state) instead of CLI-only mode
2. Use `list_projects` first to confirm the project exists
3. Run `ai-os memory reindex <path>` to refresh; this re-syncs the
   graph state

**The bug is in the binary, not in the CLI**. AI-OS works around
it by surfacing `list_projects` output in `reindex` results so
you always know what's indexed.

## 4. The loop system (phase 2)

A **loop** is a reusable claude workflow that:

- has a goal (`TASK.md`)
- has a procedure (`LOOP_INSTRUCTIONS.md`)
- has memory across runs (`PROGRESS.md`)
- writes outputs to `outputs/`

This is the pattern from Rahul (@sairahul1)'s "How to Create Loops
with Claude Code" adapted to AI-OS conventions.

### 4.1 The 4-file loop structure

Every loop directory has these 4 files:

```
my-loop/
├── TASK.md              # the goal — what this loop is trying to accomplish
├── LOOP_INSTRUCTIONS.md  # operating procedure — how claude should run
├── PROGRESS.md          # memory — what happened across runs
└── outputs/             # where claude writes results
```

Templates are at `workflows/loop_template.md` (copy-paste-ready).

### 4.2 The 6 blast-radius levels

Defined in `rules/loop_safety.md`:

| Level | Name | What it does | Examples |
|---|---|---|---|
| 1 | Read only | reads files / tickets / logs / issues | daily project review, CI log triage |
| 2 | Draft outputs | writes to `outputs/` only | PR review draft, standup note |
| 3 | Sandbox edits | modifies files inside a controlled sandbox | code refactor in feature branch |
| 4 | Draft external actions | prepares but does NOT send | PR description, Slack draft |
| 5 | Human-approved actions | applies changes only after explicit human approval | merge PR, send email |
| 6 | Automated low-risk actions | completes narrowly scoped tasks automatically | daily backup, weekly housekeeping |

**Rule: Level ≤ 3 by default.** Promotion requires 5+ successful
manual runs at the prior level, recorded in `PROGRESS.md`.

### 4.3 The `ai-os loop` CLI

```
ai-os loop <subcommand> [args]
```

| Subcommand | Purpose |
|---|---|
| `ls` | List registered loops |
| `add <dir>` | Register a loop (requires TASK.md + LOOP_INSTRUCTIONS.md) |
| `rm <id>` | Mark as removed (keeps the directory) |
| `status <id>` | Show loop files state + level + last activity |
| `show <id>` | Cat the loop's `PROGRESS.md` |
| `show PROGRESS.md` | Cat the cross-loop `PROGRESS.md` |
| `pause <id>` | Disable scheduling for a loop |
| `run <id>` | Open Terminal at loop dir + print the run prompt |

The loop registry is plain text at
`memory/loop_state/registry.txt`:

```
# format: id|directory|level|status|created_at
my-loop|/path/to/my-loop|2|active|2026-07-07T13:55:07Z
```

Pure text → grep-friendly → any CLI can read it.

### 4.4 End-to-end flow

```bash
# 1. Create the loop directory + copy templates
mkdir -p ~/my-loop/outputs
cp /Users/edd/Projects/ai-os/workflows/loop_template.md /tmp/_ref.md
# copy the 3 templates from there into TASK.md, LOOP_INSTRUCTIONS.md, PROGRESS.md

# 2. Fill TASK.md and LOOP_INSTRUCTIONS.md (PROGRESS.md starts empty)

# 3. Run manually 3-5 times
cd ~/my-loop
# paste the run prompt from LOOP_INSTRUCTIONS.md into hermes/claude/codex

# 4. After 3-5 manual runs that work, register
ai-os loop add ~/my-loop

# 5. Schedule via Hermes
hermes cronjob create --prompt "$(cat ~/my-loop/PROMPT.md)" \
  --schedule "0 9 * * *" --workdir ~/my-loop --name "my-loop-daily"
```

The `workflows/loop_template.md` provides copy-paste templates for

## 5. Skills (loadable from any agent)

Skills live in `ai-config/skills/<name>/SKILL.md`. Frontmatter is
YAML + the description field is the trigger (≤1024 chars).

### 5.1 Memory skills (phase 1)

#### `ai-os-memory`

**When it loads**: any time the user asks about persistent state,
graph queries, indexing repos, or starting the memory stack.

**What it does**:
- Reports the four-service health (FalkorDB, Ollama, cbm, grepai)
- Tells the agent which URL to open for which data
- Walks the agent through `ai-os memory <sub>`
- Triggers reindex when the user changes project code

#### `ai-os-loop` (phase 2)

**When it loads**: any time the user asks "create a loop", "automate
this daily", "schedule this review", "make a recurring workflow", or
mentions `PROGRESS.md` / `LOOP_INSTRUCTIONS.md` / "my-loop".

**What it does**:
- Asks the user which blast-radius level the loop should start at
- Helps fill `TASK.md` and `LOOP_INSTRUCTIONS.md`
- Runs the loop 3-5 times manually before scheduling
- Registers via `ai-os loop add`

### 5.2 AI-OS core skills (always available)

| Skill | Purpose |
|---|---|
| `using-superpowers` | Router — at the start of every task |
| `brainstorming` | If the idea is vague |

| `executing-plans` | Execute block by block |
| `verification-before-completion` | Between blocks |
| `code-review-and-quality` | Before PR |
| `finishing-a-development-branch` | At the end |
| `workflows/project_start.md` | AI-OS-native: produce a Spec in `specs/current_spec.md` |
| `workflows/daily_start.md` | AI-OS-native: start-of-session loading |
| `workflows/coding.md` | AI-OS-native: code work |


### 6.1 The 10MCPs (current as of 2026-07-07)

| MCP | Command | Purpose |
|---|---|---|
| `agent-browser` | `npx -y @playwright/mcp` | Browser automation (Playwright) |
| `chrome` | `npx -y chrome-devtools-mcp` | Chrome DevTools Protocol |
| `codebase-memory-mcp` | `/Users/edd/.local/bin/codebase-memory-mcp` | AST knowledge graph of code |
| `filesystem` | `npx -y @modelcontextprotocol/server-filesystem` | Local file ops |
| `graphiti` | `uv run --with graphiti-core[falkordb] --python 3.11 python -m graphiti_mcp_server` | Temporal knowledge graph → FalkorDB |
| `grepai` | `/Users/edd/.local/bin/grepai mcp` | Semantic code search |
| `memory` | `npx -y @modelcontextprotocol/server-memory` | Built-in memory store |
| `pdf` | Python-based PDF tooling | Read, fill, extract from PDFs |
| `sequential-thinking` | `npx -y @modelcontextprotocol/server-sequential-thinking` | Multi-step reasoning |
| `time` | `npx -y @modelcontextprotocol/server-time` | Time utilities |

### 6.2 Generating the config

```bash
# Regenerate from YAMLs:
python3 /Users/edd/Projects/ai-os/setup/generate-mcp-config.py \
  /Users/edd/Projects/ai-os/ai-config/mcp \
  /Users/edd/.hermes/config.yaml
```

The generator:

- Walks every `*.yaml` in `ai-config/mcp/`
- Expands `${HOME}` and `${USERPROFILE}` to absolute paths (so
  Hermes, Claude Code, Codex, etc. don't have to handle env
  expansion themselves)
- Backs up the previous config to `~/.hermes/config.yaml.pre-aios.bak`
- Writes the new config with all servers under `mcp_servers.<name>`

### 6.3 MCP paths (canonical)

All binary MCPs use **absolute paths** in the config:

```yaml
# ai-config/mcp/codebase-memory-mcp.yaml
command: /Users/edd/.local/bin/codebase-memory-mcp
args: []
```

The generator refuses to write `${HOME}` literals — `ai-os memory
status` would show `! not in config` if any path failed to expand.
If you see that, run the generator manually.

### 6.4 Configuring `graphiti` (the FalkorDB writer)

Graphiti is theMCP that actually populates FalkorDB with entities.
`ai-config/mcp/graphiti.yaml` env block:

```yaml
env:
  FALKORDB_HOST: localhost
  FALKORDB_PORT: "6390"
  FALKORDB_URL: redis://localhost:6390
  GRAPHITI_GROUP_ID: aios
  OPENAI_API_KEY: ${OPENAI_API_KEY}    # required: graphiti uses OpenAI embeddings
```

If `OPENAI_API_KEY` is unset, graphiti will fail at startup. Set
it in `~/.env` (or pass via the env block after expansion).

## 7. The Spec → Verifier → Environment method

This is the heart of AI-OS. It comes from Karpathy's
[How to Get the Most Out of LLM Coding Agents](https://www.youtube.com/watch?v=VC6J7kkJM0s).

### 7.1 The flow

```
1. Read  CLAUDE.md + relevant context/ files
2. Check specs/current_spec.md
   └─ If empty → workflows/project_start.md
3. Execute in blocks of ≤30 min
   └─ Between blocks → verifiers/critic_prompt.md
4. Archive completed Specs to archive/YYYY-MM-DD-<slug>.md
```

### 7.2 Spec anatomy

A Spec has:

- **Goal** (one paragraph, what success looks like)
- **Constraints** (what NOT to do, what the blast-radius is)
- **Plan** (numbered blocks of ≤30 min)
- **Per-block subtasks** (so you can resume mid-block)
- **Verifiers** (what command to run between blocks)
- **Archive summary** (1-line summary of outcome)

### 7.3 Active Specs and archive

```
specs/
├── current_spec.md              # active (or empty)
├── spec_template.md              # starting point
archive/
└── YYYY-MM-DD-<slug>.md
```

`specs/current_spec.md` is reserved for one active task. Completed task records
are versioned in `archive/`; archive entries must not overwrite one another.

## 9. Common commands (cheat sheet)

```bash
# ==== MEMORY ====
ai-os memory status                       # health of all 4 services
ai-os memory browse                       # open FalkorDB UI
ai-os memory visualize                    # open FalkorDB + cbm UIs
ai-os memory search "<q>" ~/Projects      # semantic code search (tier 1+2)
ai-os memory reindex /Users/edd/Projects   # index AST of a repo
ai-os memory query "<q>" ~/Projects       # grepai-only semantic search
ai-os memory sync-sessions 90             # ingest last 90 days of Hermes sessions
ai-os memory logs                         # tail FalkorDB logs
ai-os memory start / stop                 # FalkorDB lifecycle

# ==== LOOPS ====
ai-os loop ls                             # list registered loops
ai-os loop add <dir>                      # register a loop
ai-os loop status <id>                    # show loop state + level
ai-os loop show <id>                      # cat PROGRESS.md
ai-os loop show PROGRESS.md               # cross-loop log
ai-os loop pause <id>                     # disable scheduling
ai-os loop rm <id>                        # mark as removed
ai-os loop run <id>                       # open Terminal + print run prompt

# ==== MCP / SERVICES ====
docker ps --format '{{.Names}}\t{{.Status}}'  # all containers
docker exec ia-os-falkordb redis-cli -p 6379 PING  # Redis ping
curl -s -m 3 http://localhost:11500/api/tags | jq .  # Ollama models
curl -sI -m 3 http://localhost:3300/ | head -1       # FalkorDB Web
curl -sI -m 3 http://localhost:9749/ | head -1       # cbm UI

# ==== INSTALL / VERIFY ====
bash ~/Projects/ai-os/setup/install-mac.sh   # full install (idempotent)
bash ~/Projects/ai-os/setup/verify.sh        # 38-check verifier
python3 ~/Projects/ai-os/setup/generate-mcp-config.py \
  ~/Projects/ai-os/ai-config/mcp \
  ~/.hermes/config.yaml                      # regenerate MCPs

# ==== AI-OS WORKFLOW ====
cat ~/Projects/ai-os/AGENTS.md              # read agent instructions
cat ~/Projects/ai-os/specs/current_spec.md  # active Spec (or empty)
ls ~/Projects/ai-os/archive/                # completed Specs
```


### 10.3 `Ollama not running`

Known bug in `codebase-memory-mcp` v0.8.1. Workarounds:

## 11. Security model

### 11.1 No secrets in repo

- `.env.example` documents the env shape
- The real `~/.hermes/.env` lives in your home dir, never in the repo
- `.gitignore` blocks `.env`, `node_modules/`, `dist/`, `build/`

### 11.2 Blast-radius discipline

- Every loop declares its level in `TASK.md`
- Levels 4+ require explicit human promotion, recorded in `PROGRESS.md`
- No loop can do `rm -rf` outside its own `outputs/` without
  reaching the verification checklist first

### 11.3 Dependency surface

- `codebase-memory-mcp` reads your code, writes to your agent config
  (that's its design — see its README)
- `grepai` is privacy-first, all-embedding baked in, no API key
- `graphiti` requires `OPENAI_API_KEY` (cost consideration)
- `Ollama` runs locally, no data leaves your Mac
- `FalkorDB` is a local Docker container, data stays in `./data/`

### 11.4 What we DON'T do

- No outbound telemetry
- No third-party identifier tagging
- No `.env` for non-secret config (see `rules/always_do.md` and
  `rules/never_do.md`)
- No "delete to clean up" workflows — all data has a clear lifecycle
  (loop_state dir is in `memory/`; can be removed safely; does
  not delete loop directories)

## 14. Quick start (90 seconds)

```bash
# 1. Install everything (idempotent):
bash ~/Projects/ai-os/setup/install-mac.sh

# 2. Verify:
bash ~/Projects/ai-os/setup/verify.sh
# Expected: 38 passed, 0 failed. Banner: "AI-OS is correctly installed. 🎉"

# 3. Open new terminal so PATH updates apply:
exec zsh

# 4. Check memory stack:
ai-os memory status

# 5. Index your projects:
ai-os memory reindex /Users/edd/Projects

# 6. Search semantically:
ai-os memory search "where is the Spec+Verifier loop" /Users/edd/Projects

# 7. Open the browser:
ai-os memory visualize

# 8. Create your first loop:
mkdir -p ~/my-loop/outputs
cp ~/Projects/ai-os/workflows/loop_template.md /tmp/_ref.md
# (fill TASK.md and LOOP_INSTRUCTIONS.md from the template)
ai-os loop add ~/my-loop
ai-os loop ls

# 9. Talk to it:
hermes chat --skills ai-os-memory,ai-os-loop
```

Done. You now have a fully spec-verifier-environment loop, a
persistent-memory stack, and a loop orchestration CLI. All on
your Mac, all vendor-neutral.
