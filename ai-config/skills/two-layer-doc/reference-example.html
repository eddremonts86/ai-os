AI-OS · opening the project to other people

Three decisions before AI-OS can be shared

Each point shows how it works today, what we propose and the one choice we need. For the project owner, about 15 minutes.

1 · Skills that belong to one person

Owner decides

Today: every skill folder in the project (174 now) is linked into each AI tool on every machine that installs AI-OS. A skill that only makes sense for one person, for example one about their own servers or employer, would reach everyone.

Proposal

Add a second, private place for personal skills and let the installer link it with the shared ones.

Decision

Choice: add the private place now, or keep every skill generic and move personal facts into notes.

Our recommendation: not yet. One skill (form audits) still carries a company profile; make that one generic first, and build the private place when a second case shows up.

2 · A security check that GitHub runs

Owner decides

Today: before a push, a check on the developer's machine scans the new code for secrets and serious flaws, and blocks the push if it finds one. Anyone can skip it. GitHub's own tests do not run that scan.

Proposal

Run the same scan on GitHub for every pull request. A failure shows red on the pull request; it does not stop the merge by itself.

Decision

Choice: add the scan on GitHub, or keep it on the developer's machine only.

Our recommendation: add it. It is the same scan we already trust, and the red mark no longer depends on one person's machine.

3 · The first run for a new user

Owner decides

Today: after installing, a new user gets blank templates and has to find and fill in several files to tell AI-OS who they are. Until then the tools read placeholders and answer in the default language.

Proposal

Ask for the name and the chat language during install, write them in the right places, and skip the questions on automated installs.

Decision

Choice: ask two questions, or ship the templates only.

Our recommendation: ask. The chat language is what makes every tool answer in the user's language from the first message.

1 · A private place for skills

  • Today. Step 7 of setup/install-mac.sh loops over ai-config/skills/*/ and links every folder with a top-level SKILL.md into each client path of ai-config/manifest.yaml (.claude/skills, .codex/skills, .gemini/skills, .agents/skills, optional .minimax/skills). install-windows.ps1 does the same from its own loop. Verified in the code today: 174 folders.
  • Design. Add context/personal/skills/ (git-ignored) as a second source in the same loop. setup/ai-os-skills.py and the frontmatter check in setup/hooks/pre-push glob only ai-config/skills/, so both must read the new folder or personal skills escape the description budget.
  • Does not change. The shared skills, the client list, and the backup, which already archives context/personal/.
  • Tests. One in setup/tests: a skill in the private folder is linked, and a stale link to a removed one is pruned.
  • Effort and waits. Our assumption, not measured: small, one loop plus one glob. First real case: the company profile under optimizing-forms/references/profiles/.

2 · The scan on GitHub

  • Today. setup/hooks/pre-push runs ai-config/skills/aios-security-audit/scripts/scan.py . --baseline <ref>: gitleaks, semgrep, osv-scanner, trivy and hadolint on what the push adds, exit 1 on a critical or high finding. Measured on this repo: about 6 seconds. The workflows in .github/workflows/ (Linux, macOS and Windows tests, apps, image, guard-main, deploy-site) never call scan.py.
  • Design. A security.yml on pull_request to dev and main: checkout with full history, install the five scanners on the runner, run scan.py against the base branch, publish summary.md as the job summary.
  • Does not change. The local hook stays. A scanner that is not installed is reported as NOT RUN, never as clean, on both sides.
  • Not known. Runner install time: probably minutes, to measure. Branch protection: the note in the pre-push hook says it needs a paid plan, so a red check is a signal and not a block; not re-checked today.
  • Tests. Open a pull request on a scratch branch with a planted fake private key; the job must fail and name the file.

3 · Questions on first run

  • Today. setup/seed-personal-context.py copies context/personal.example/ to context/personal/ and never overwrites. apps/create-ai-os/bin/create-ai-os.js then prints "describe yourself in context/personal/". install-mac.sh already skips its prompts when ASSUME_YES=1 or there is no TTY.
  • Design. After seeding, on a TTY and without ASSUME_YES, ask the name and the chat language. Write the identity lines of 00_profile.md and a one-line bridge.md, only when the file still equals its template. Windows asks the same through Read-Host.
  • Does not change. Non-interactive installs and CI; a file the user already edited is never touched.
  • Tests. A unit test on the writer function with a temporary root: fills a template, skips an edited file, skips with no answer.
  • Not known. Windows path: cannot be run here (no pwsh); CI covers the dry run only. Free text for the language, or a short list: open.
